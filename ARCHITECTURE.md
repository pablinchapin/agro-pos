# Agro POS — Architecture

## Request Flow

```
Streamlit (sync httpx.Client)
│
▼ HTTP JSON
FastAPI + Uvicorn (async)
│
├── api/v1/endpoints/     validates input (Pydantic), delegates to service
├── services/             business rules, domain exceptions, orchestration
├── repositories/         async SQL via SQLAlchemy 2.0 + asyncpg
│
└── PostgreSQL (via kubectl port-forward in dev, direct in prod)
```

Note: Streamlit uses sync `httpx.Client` (wrapped in `st.cache_resource`).
The FastAPI backend is fully async. These are deliberately different —
Streamlit's execution model is synchronous per script run.

## Layer Responsibilities

| Layer | Responsibility | May import from |
|---|---|---|
| endpoints | HTTP in/out, input validation, response shaping | services, schemas |
| services | Business rules, domain exception raising, multi-entity orchestration | repositories, schemas, models |
| repositories | Async DB queries only, return ORM objects | models, AsyncSession |
| models | SQLAlchemy table definitions (`Mapped[]` style only) | db/base.py |
| schemas | Pydantic I/O contracts (`Create`/`Update`/`Response`) | — |

## Key Design Decisions

1. **Async SQLAlchemy 2.0 from v1** — chosen for future SaaS scalability with
   concurrent multi-tenant traffic. Uses `asyncpg` driver and `AsyncSession`.
   All repository methods are `async def`. No sync/async mixing allowed.

2. **Repository pattern** — DB access is fully encapsulated in `repositories/`.
   Services never import SQLAlchemy directly. This makes unit testing clean:
   mock the repository, test the service logic in isolation with `AsyncMock`.

3. **Domain exceptions over HTTPException** — services raise typed domain exceptions
   (`NotFoundError`, `DuplicateError`, `InsufficientStockError`). These are mapped
   to HTTP status codes once in `main.py` via global exception handlers. Endpoints
   stay clean — no try/except blocks.

4. **Person with roles** — a single `Person` entity with role (`customer`, `farmer`,
   `both`) avoids data duplication when the same individual buys inputs and sells
   grains. Role validation is enforced at the service layer, not at the DB level.

5. **Alembic for all schema changes** — migration files are auto-generated and always
   reviewed before applying. Never ALTER TABLE manually.

6. **Streamlit multi-page with explicit navigation** — two audience sections (`pos/`
   and `admin/`) defined via `st.Page()` in `app.py`. No numeric filename prefixes.
   No auth in v1 — access control is v2 scope.

7. **RBAC with JWT** — authentication uses python-jose for JWT signing and
   passlib[bcrypt] for password hashing. Three FastAPI dependencies handle
   authorization: `get_current_user()` (any authenticated user),
   `require_admin()` (admin only), `require_clerk()` (admin or clerk).
   Dependencies are applied per-endpoint via `Depends()` — no middleware,
   no decorators.

## Frontend Design Decisions

1. **Two audiences, one app** — `pos/` (cashier) and `admin/` (owner/manager)
   are separated into distinct folders, grouped visibly in the sidebar via
   `st.navigation()`. Same Streamlit process, different page sets.

2. **Sync httpx in frontend** — Streamlit re-runs the entire script top-to-bottom
   on each interaction. Async HTTP clients add complexity with no benefit here.
   The shared `httpx.Client` is cached via `st.cache_resource`.

3. **No React-style component isolation** — `shared/components.py` holds reusable
   rendering functions, but all pages share global `st.session_state`. There is no
   prop system or isolated component lifecycle.

4. **Auth via JWT in frontend** — both `pos/` and `admin/` require authentication.
   Login page stores the JWT in `st.session_state`. The shared `api_client.py`
   includes the Bearer token in every request header automatically.
   Role-based page visibility: `admin` sees both sections, `clerk` sees only `pos/`.

5. **Inventory is admin-only in UI** — although the backend allows clerk 
   access to /inventory/ endpoints, the frontend restricts inventory 
   visibility to admin only. Clerks can see product stock indirectly 
   when registering a sale (InsufficientStockError feedback).

## Database Schema

```
Table             Fields                                                         Status
──────────────────────────────────────────────────────────────────────────────────────
products          id, name, category, unit, price, stock, min_stock,            ✅ done
                  created_at

persons           id, full_name, phone, role (customer|farmer|both),            ✅ done
                  notes, created_at

grain_types       id, name, unit                                                 ✅ done
                  (seed data: Café, Maíz, Frijol — all lb)

grain_inventory   id, grain_type_id (FK→grain_types), total_stock               ✅ done

grain_purchases   id, person_id (FK→persons), grain_type_id (FK→grain_types),   ✅ done
                  weight, price_per_unit, total, date, notes

sales             id, person_id (FK→persons), date, total_amount, notes         ✅ done

sale_items        id, sale_id (FK→sales), product_id (FK→products),             ✅ done
                  quantity, unit_price, subtotal

users             id, username, hashed_password, role (admin|clerk),            ⬜ next
                  is_active, created_at
```

### Key relationships
- `persons` → `sales` (one person, many sales)
- `persons` → `grain_purchases` (one person, many grain purchases)
- `products` → `sale_items` (one product, many sale line items)
- `grain_types` → `grain_purchases` (one grain type, many purchases)
- `grain_types` → `grain_inventory` (one grain type, one inventory record)
