# Agro POS — Claude Code Context

## Project
Point of Sale system for a Guatemalan agricultural supply store (agroservicio).
Two commercial flows:
- **Outbound**: selling agricultural inputs (seeds, fertilizers, herbicides, fungicides)
- **Inbound**: purchasing grains from farmers (coffee, corn, beans)

For full domain definitions, business rules, and module scope → see SPEC.md
For architecture diagrams and DB schema → see ARCHITECTURE.md

## Tech Stack
- Python 3.9.6
- FastAPI + Uvicorn (REST API, async)
- PostgreSQL + SQLAlchemy 2.0 async + Alembic (database & migrations)
- Pydantic v2 (data validation)
- Streamlit (POS frontend UI)
- HTTPx (HTTP client)
- pytest (testing)

## Commands
- **Run API**: `cd backend && uvicorn app.main:app --reload --port 8000`
- **Run UI**: `cd frontend && streamlit run app.py`
- **Migrate DB**: `cd backend && alembic upgrade head`
- **New migration**: `cd backend && alembic revision --autogenerate -m "description"`
- **Run all tests**: `cd backend && pytest tests/ -v`
- **Run unit tests**: `cd backend && pytest tests/unit/ -v`

## Architecture Patterns
- **Endpoints**: thin and async — validate input via Pydantic, delegate to service, return schema. No business logic here.
- **Services**: all business rules live here. Call repositories. Raise domain exceptions (never HTTPException).
- **Repositories**: async DB queries only. Receive `db: AsyncSession`. Return ORM objects, never Pydantic schemas.
- **Models**: SQLAlchemy 2.0 `Mapped[]` / `mapped_column()` style only — never legacy `Column()`.
- **Schemas**: Pydantic v2. `Create` / `Update` / `Response` pattern. `Decimal` for money fields.
- **Dependency injection**: `Depends(get_db)` for DB session. Services instantiated inside endpoints.

## Conventions
- `snake_case` for all Python identifiers
- Table names: plural `snake_case` (`products`, `grain_purchases`, `persons`)
- Schema class names: `PascalCase` with suffix (`ProductCreate`, `ProductResponse`)
- Service methods: `verb_noun` (`create_sale`, `get_product_by_id`, `reduce_stock`)
- Repository methods: same `verb_noun` pattern, always `async def`
- Never use `import *`
- All endpoints return Pydantic schemas — never raw ORM objects

## Agent Behavior
When implementing a full module (model → schema → repository → service → endpoint → tests → docs):
1. Always read relevant skills in `.claude/skills/` before writing any file
2. Always implement in this order: model → schema → repository → service → endpoint → register router in main.py
3. Always generate and apply Alembic migration after creating a new model:
   `source ../.venv/bin/activate && cd backend && alembic revision --autogenerate -m "create <entity> table" && alembic upgrade head`
4. After implementation, invoke @agent-test-writer — only continue when all tests pass
5. After tests pass, invoke @agent-documenter for the completed module
6. If a skill and your training conflict, the skill wins

## Available Agents
- `@agent-module-implementer` → full CRUD module from model to endpoint, in strict layer order
- `@agent-test-writer` → unit and integration tests, never modifies source code
- `@agent-documenter` → Mermaid diagrams saved to `docs/diagrams/`

All MCP credentials loaded from `.env` — never hardcoded. See `.env.example`.

## Do NOT
- Put business logic in endpoints
- Query the database directly in services
- Use legacy `Column()` style in SQLAlchemy models — always use `Mapped[]`
- Mix sync and async DB calls — every repository method must be `async def`
- Use `requests` library — always use `httpx` (async in backend, sync in frontend)
- Skip Alembic migrations — never ALTER TABLE manually
- Hardcode credentials anywhere in source code or config files
- Duplicate domain concept definitions — those live in SPEC.md only
